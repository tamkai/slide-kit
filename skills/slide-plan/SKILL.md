# slide-plan — スライドの構成をつくる（第1段階）

**ユーザーとのやり取りは必ず日本語で行う。**

原稿・ネタ・トピックを読み、スライド1枚=1メッセージに分解した **構成JSON（`deck_structure.json`）** を作る。**このスキルはスライドそのものを作らない。** 作るのは構成だけ。

## なぜ二段階なのか（利用者に必ず伝えること）

「スライド作って」と一息で頼むと、AIは構成（話の順番・枚数配分）と見た目を同時に決めてしまう。すると直したいのが構成なのに、毎回デッキ全体が作り直しになる。

**構成だけを人が読めるファイルとして一度止める**と、そこを直すだけで安く速く回せる。これが二段階の理由であり、この仕組みの心臓部。

初めて使う人には、構成JSONができた時点で必ずこう伝える:

> ここで一度止まります。話の順番・枚数・各スライドで言いたいことを見て、直すところがあれば言ってください。ここで直す方が、スライドになってから直すよりずっと速いです。

## いつ使うか

- 原稿・記事・議事録・トピックから、セミナー/プレゼンの構成を組みたい
- スライドを作る前に「何枚・各枚に何を載せるか」を先に固めたい
- 後段の slide-make でスライド化する、その第1段階

## 設計思想（重要・非自明）

- **1スライド1メッセージ**。盛り込みすぎない。詳細は手順書側へ逃がす
- **語りの軸に沿って枚数配分する**。導入 → 理解の山 → 手順 → まとめ、のように流れを設計する
- **理解の山（難所）は1枚に詰めず2枚に割ってよい**（例: 全体図 → なぜそれが本命か）
- **チェックリスト・一覧は抽象化する**（例: 16ステップ → 7フェーズの俯瞰1枚。詳細はスライドに焼かない）
- **文字は画像に焼かれる**前提で書く（タイプAの場合）。タイトルは短く（〜18字目安）、タグは2〜8字キーワード。長文・表・コードは載せない
- **世界観の連続性**を意識する。表紙の完成形 → 全体図 → まとめ が同じモチーフで呼応すると締まる

### 設計哲学のリファレンス（AI-generated look から抜けるために）

構成を組む前に、以下を読んで適用する。これらは theme/実装に依存しない普遍的な設計層。

- `references/design-principles.md` — **希少性の三原則**（色・レイアウト・記号を99%抑え、1%を効かせる）
- `references/design-modes.md` — **Document ↔ Workshop 連続軸**（visual-first ratio を案件ごとに意図して決める）
- `references/design-tension_map.md` — **Tension Map 思考**（各スライドに tension スコアを付け、緩急を設計してからレイアウトを決める）
- `references/design-accent_placement.md` — **Accent 配置5ポジション**（章扉・クライマックス・CTAへの accent 配置）
- `references/self_audit_checklist.md` — 構成が単調になっていないかの自己監査

## 構成JSONのスキーマ

各スライドオブジェクトに以下を持たせる。`assets/example_deck_structure.json` が実例（20枚のセミナー構成）。

| フィールド | 用途 |
|---|---|
| `n` | スライド番号（1始まり） |
| `title` | スライドに出す短いタイトル（最大18字目安・端的に） |
| `key_message` | 聴衆に残す1行（ナレーション用。スライドには出さない） |
| `labels` | 画作り・検索用のキーワード配列（各2〜8字・3〜6個）。**スライドに文字として焼くとは限らない**（既定は焼かない。焼く判断は slide-make 側で枚単位に行う） |
| `visual_brief` | 図1枚絵の具体的な画作り指示（英語可。何のオブジェクトをどう配置し何を表すか） |
| `source_section` | 元原稿の対応箇所（任意・トレーサビリティ用） |
| `speaker_note` | 話者メモ1〜2文（PPTXのスピーカーノートに入る） |
| `body_text` | （読ませ版用）簡潔体の説明文。`\n`区切りで2〜3行 |
| `lead_B` | （読ませ版の上下分割用）大きく置く「結論ひとこと」1行・言い切り |
| `body_B` | （読ませ版の上下分割用）敬体の本文。`\n`区切りで2〜3行 |

`lead_B` / `body_B` は**タイプA（講演用）でも基本的に焼き込む**ようになったため、原則すべてのスライドで埋める（2026-08変更: 図だけのスライドは話者依存が強すぎるため、Bと同等の情報量が既定になった）。`body_text` は旧形式で、通常は不要。

## 手順

### Step 0: 環境チェック（初回のみ・自動）

`~/.slide-kit-ready` が存在しなければ、slide-setup の手順を実行してから続行する。存在すれば黙って次へ進む。**利用者に環境の話をさせない。**

### Step 1: 素材が足りているかを判定する

対象の原稿/トピックを読み、**次の3つが取れるか**を確認する。

| | 無いとどうなるか |
|---|---|
| **聞き手は誰で、今どういう状態か** | 誰に向けたのか分からず、一般論になる |
| **聞き終わったあと何ができるようになるか** | 枚数配分が逆算できない |
| **理解の山（聞き手がどこで「え？」となるか）** | **全スライドが均等割りになり退屈になる** |

**1つでも取れないなら、構成を組まずに slide-ask を呼ぶ。**
`deck_brief.md` が既にあるなら、それを読めば全部揃っている。

ここで**「原稿を用意してください」と突き放さない。** 素材が薄いのは普通のこと。
黙って slide-ask の手順に入り、短い質問（最大5問・1問ずつ）で足りない分だけ引き出す。
利用者から見れば「構成を頼んだら、いくつか質問された」という体験になる。

3つとも取れているなら、何も聞かずに Step 2 へ進む。**揃っているのに質問しない。**

### Step 2: 語りの軸と枚数を決める

導入 → 本論（理解の山は分割）→ 手順 → まとめ、の流れで何枚にするか設計する。デフォルト16〜20枚。短時間説明なら10枚前後。

**枚数は使用量に直結する**（タイプAの画像生成は通常の3〜5倍速く枠を消費する）。20枚を超えるなら、本当に必要か一度問い直す。

### Step 3: 各スライドを設計する

サブエージェント（general-purpose）に原稿全文と本スキーマを渡し、全スライドの構成JSONを起こさせるのが効率的。プロンプトには「純粋なJSONのみ返す・全フィールド記入・末尾カンマ禁止・バリッドなJSON」を必ず指定し、`assets/example_deck_structure.json` を出力形式の見本として渡す。

### Step 4: 読ませ版用テキストを足す（読ませ版を作る場合のみ）

各スライドの `key_message` を元に `lead_B` と `body_B` を整える。専門用語は噛み砕く。画像に焼かれる場合があるので、括弧の入れ子・特殊記号を避ける。

**`lead_B` は副題でもキャッチコピーでもない。** それだけを読めば、そのスライドの主張・論点・結論が完全に理解できる文章にする。以下を1つの自然な文に統合する:

- そのスライドで扱う対象
- 中心となる主張・結論
- その結論に至る理由や構造
- 読者が理解すべき意味や示唆

**70〜105字**を目安とし、**原則2行・最大2行**に収まる量にする。根拠のない断定・推測はしない。

#### 読み物型（slide-make のタイプA-2）を作る場合の文体

**です・ます調も、だ・である調も使わない。** 簡潔で端正な説明調にする。

- 使う: 体言止め / 動詞の連体形・終止形 / 「〜する構造」「〜という位置づけ」「〜が必要」「〜につながる可能性」 / 「〜により」「〜を通じて」「〜を前提に」
- 使わない: です・ます・でした・ました・でしょう・だ・である・となるのである
- **体言止めを連続させて単語の羅列にしない。** 主語と述語、理由と結論、前提と意味の関係が伝わる文章の流れを保つ
- 同じ文末形式を機械的に繰り返さない
- 報告書・解説記事に適した客観的で落ち着いた文体。会話的表現・呼びかけ・感嘆・過度な断定を使わない

この文体は `title` / `lead_B` / `body_B` のすべてに適用する。詳細 → `../slide-make/references/type-a-readable.md`

**この文体規定は読み物型のときだけ適用する。** 講演用（A-1）や通常のHTML（B）では、素直な敬体でよい。

### Step 5: 検証して保存し、**人に見せて止まる**

```bash
python3 -c "import json; json.load(open('deck_structure.json'))"
```

でバリッドを確認したら、**タイトル一覧を出してユーザーに提示し、レビューを求めて止まる**。ここで勝手に slide-make へ進まない。

出力先は**作業プロジェクト配下**にする（`~/.claude/` や プラグイン配下に書かない。タイプAで使う codex がそこに書けないため、後段で詰まる）。

## 前段

原稿・素材は **slide-ask** で作る（`deck_brief.md`）。素材が足りないときは自動で呼ぶ（Step 1）。

## 次の段階

構成が固まったら **slide-make** でスライド化する。「これを画像スライドにして」「これを編集できるスライドにして」で発動する。
