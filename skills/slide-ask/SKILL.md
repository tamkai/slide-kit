# slide-ask — 原稿・素材をつくる（第0段階）

**ユーザーとのやり取りは必ず日本語で行う。**

話し手の頭の中にあるものを引き出し、足りない事実を補って、**slide-plan に渡せる原稿ブリーフ**（`deck_brief.md`）を作る。

## いつ使うか

- 原稿がない。テーマだけある
- ネタはあるが整理できていない
- 原稿はあるが薄い（一般論だけで、具体例も山場もない）
- slide-plan が「素材が足りない」と判断したとき（自動で呼ばれる）

**既に十分な原稿がある場合は使わない。** slide-plan に直行してよい。

## 大原則（これを外すとこのスキルは害になる）

### 1. 抽象を聞かない。経験を聞く

**「コアメッセージは何ですか？」と聞かれて答えられる人はいない。** 人は抽象を語れないが、経験は語れる。

| ✗ 聞かない | ○ 聞く |
|---|---|
| コアメッセージは？ | この話をして、ポカンとされたことは？ |
| 課題は何ですか？ | 直近でうまくいかなかった例は？ |
| 独自性は？ | 「それ知らなかった」と一番言われるのは？ |
| ターゲットは？ | 直近で誰にこの話をしましたか？ |

抽象的な問いは、相手を止める。具体的な問いは、相手を喋らせる。

### 2. 質問は最大5問。一度に1問だけ

**20問聞くくらいなら、このスキルは無い方がマシ。** まとめて列挙して投げない。1問ずつ、答えを聞いてから次を決める。

相手の答えが厚ければ、質問を減らして早く切り上げる。**足りない穴だけ聞く。**

### 3. ヒアリングが先。リサーチは穴埋めだけ

- **ヒアリング** = 本人の頭の中にあるが、言語化されていないものを引き出す
- **リサーチ** = 本人が知らない事実（数字・現状・一次情報）を埋める

**順番を逆にしない。** 先に調べると、本人が語れることまで調べに行って、
「どこかで読んだ話」になる。**原稿の価値は本人の中にしかない情報に集中している。**

### 4. 書かせない。喋らせる

相手が「文章にしないと」と思った瞬間に止まる。最初にこう伝える:

> 文章にしなくて大丈夫です。箇条書きでも、思いついた順でも構いません。
> 音声入力が使えるなら、**誰かに説明するつもりで喋ってもらう**のが一番速くて濃く出ます。

## 手順

### Step 1: 今あるものを受け取る

まず、既にあるもの（メモ・記事・議事録・過去のデッキ・文字起こし）を全部出してもらう。
**無ければ無いで進む。** ここで「ちゃんとした原稿を用意してください」と言わない。

受け取ったら、次の6つが埋まっているかを内心で確認する。**これがこのスキルの採点表**:

| | 項目 | 無いとどうなるか |
|---|---|---|
| 1 | **聞き手は誰で、今どういう状態か** | 誰に向けたのか分からず、一般論になる |
| 2 | **聞き終わったあと、何ができるようになるか** | 構成が逆算できない |
| 3 | **なぜ今この話なのか** | 聞く理由がなく、興味を持たれない |
| 4 | **理解の山（聞き手がどこで「え？」となるか）** | **枚数が均等割りになり退屈になる** |
| 5 | **具体例・失敗談・数字** | AIが書ける一般論だけになる |
| 6 | **結論と、その根拠** | 話が着地しない |

### Step 2: 足りないものだけを聞く（最大5問・1問ずつ）

**埋まっている項目は聞かない。** 穴だけ聞く。以下は聞き方の例。そのまま読み上げず、相手の文脈に合わせて言い換える。

**① 聞き手（誰に）**
> 直近で、この話を誰にしましたか？ その人は普段どんな仕事をしている方ですか？

**② 狙い（何ができるようになるか）**
> それを聞いた人に、**明日から何か1つだけ**やってほしいとしたら、何ですか？

**③ なぜ今**
> なぜ今この話をするんでしょう。何かきっかけになった出来事はありますか？

**④ 理解の山（最重要）**
> この話をしていて、**相手がポカンとする**のはどのあたりですか？
> あるいは「そこが引っかかる」と必ず言われる箇所は？

**⑤ 具体（差別化の源泉）**
> 「それ知らなかった」と一番言われるのはどれですか？
> うまくいかなかった例はありますか？

**⑥ 結論**
> 結局のところ、一番言いたいことを一言にすると？

答えが薄いときは、**一段だけ具体に降りて聞き返す**（「たとえば直近だと？」「実際どのくらいでした？」）。
2回聞いても出てこなければ諦めて次へ行く。粘りすぎない。

### Step 3: リサーチで穴を埋める（必要な場合のみ）

**本人が知らない事実だけ**を調べる。ヒアリングで出たことを調べ直さない。

調べる価値があるのは:
- 数字・データ（相手が「たしか3割くらい」と言った箇所の裏取り）
- 製品仕様・価格・サービスの現状（**知識が古い可能性があるので必ず調べる**）
- 一次情報の所在（公式ドキュメント・原典）

調べたら、**出典を原稿に併記する**。後で本人が確認できるようにする。
**本人の主張と、調べた事実を混ぜて書かない。** 区別できる形で残す。

不確かなことは「未確認」と書く。**推測を事実として書かない。**

### Step 4: 原稿ブリーフにまとめて、**見せて止まる**

`deck_brief.md` として作業プロジェクト配下に保存する。テンプレートは
`references/brief_template.md`。

**まとめたら必ずユーザーに見せて、レビューを求めて止まる。** 勝手に slide-plan へ進まない。

こう伝える:

> 聞いた内容をまとめました。**特に「理解の山」と「具体例」が合っているか**を見てください。
> ここがずれていると、スライドの枚数配分がずれます。
> 足りないところ・違うところがあれば言ってください。

### Step 5: slide-plan へ渡す

ブリーフが固まったら slide-plan を呼ぶ。ブリーフの内容がそのまま
`deck_title` / `audience` と、各スライドの設計根拠になる。

## やらないこと

- **整った文章にしようとしない。** 原稿は素材であって作品ではない。箇条書きで十分
- **この段階で削らない。** 削るのは slide-plan の仕事。素材は多めに残す
- **本人が言っていないことを書き足さない。** 埋めたくなったら聞くか、調べて出典を付ける
- **20問聞かない。** 5問で足りなければ、それ以上聞いても出てこない

## 出力先

作業プロジェクト配下に置く（`~/.claude/` やプラグイン配下に書かない）。

```
<作業プロジェクト>/<デッキ名>/
└── deck_brief.md   ← このスキルの成果物
```
